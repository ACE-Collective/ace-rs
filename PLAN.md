# ACE rebuild plan

This plan breaks [DESIGN.md](DESIGN.md) into steps that are each one reviewed change. Every step says what to build and ends with "Done when", the check that shows it works.

Phase 0 sets up the workspace and takes the first build measurement. Phases 1 to 4 follow DESIGN.md's *Sequence* steps 1 to 4, except that phase 3 compares against ace3 on local samples instead of production traffic. Sequence step 5 is split into phases 5 to 7.

Paths that start with `ace3/` are in the checkout at `../ace3`, read at commit `141a60a2` on 2026-10-29. Issue numbers are in [ACE-Collective/ace3](https://github.com/ACE-Collective/ace3/issues). The table at the end maps each of the 43 design-flaw issues to the step that removes its cause.

## Scope

For now ace4 is a proof of concept that runs on one laptop beside ace3. ace3 sends ace4 nothing. The comparisons use files already on the laptop, because the SVS corpus lives in production. Moving data out of ace3, comparing against production traffic, production deployment and cutover wait until there's a decision to take ace4 further. *Deferred* at the end lists them.

## Rules for every step

- A step is one change, with its tests in the same change.
- A step needs the steps above it in its phase, unless it names its own dependencies.
- A measurement records the command, the number of runs, the median and the range, and what else the number could include, such as cached work, errors or skipped steps.
- A ported module is done when its output matches ace3's: on reference dumps in phase 1 (1.24), and in 3.3's comparison over the local samples from phase 3 on, by the threshold in `docs/acceptance.md`. From phase 5 on, a port also brings its analysis template.
- No step changes ace3's checkout, the signatures repository or the site_ace repository. Scripts that need ace3's code live in `tools/ace3/` and run in ace3's dev container through `docker exec`.
- A step that ports something ace3 integrations can extend also adds it to `ace-app` (2.31), so site_ace can extend it too.
- A step that changes a Compose file keeps ace4's stack able to run beside ace3's, following *Running beside ace3* below. 0.6's check enforces it.

## Running beside ace3

ace4's stack has to run on the laptop at the same time as ace3's. ace3 keeps its own instances apart by project name, host ports and image tags (`ace3/docs/MULTI_INSTANCE.md`), and ace4 stays clear of all three.

- **Project name.** ace4's Compose file sets `name: ${ACE4_STACK:-ace4}`. ace3's default project is `ace`, and its extra instances take their names from `ACE_STACK`, so no ace3 instance may be named `ace4`. Compose derives container, network and volume names from the project name, so ace4 sets no `container_name` and gives no volume or network an explicit `name:`. `COMPOSE_PROJECT_NAME` overrides `name:` in both stacks, so ace4's `stack-guard` service refuses to start the stack when the project in use isn't `ACE4_STACK`. Compose can't tell that variable set to `ace4` from not set at all, so unlike ace3's `docker/startup/initialize_volumes.sh`, the guard refuses a different name rather than any value.
- **Variables.** Every ace4 variable starts with `ACE4_`, so a shell that exports ace3's `ACE_*` variables doesn't change ace4.
- **Host ports.** ace3 fixes five by default: 5000, 5001, 8443, 9443 and 24224. Each extra ace3 instance shifts all five by its offset, such as 100. ace4 fixes one, `ACE4_PORT_HTTPS` (default 7443), for the `ace` service. Postgres, the bucket and everything else publish on ephemeral ports bound to `ACE4_BIND_ADDRESS` (default `127.0.0.1`), as ace3's databases do.
- **Logs.** The stack logs to stdout. It doesn't use Docker's fluentd log driver, because that driver needs a fixed host port, and ace3 already holds 24224.
- **Images.** Every image ace4 builds is named `ace4-*`. ace3 builds `ace3`, `phishkit`, `phishkit-manager`, `js-deobfuscator` and `js-deobfuscator-manager`, all tagged `latest`, and a build in one checkout must not replace the other's images.
- **ace3's data.** ace4 reads ace3's data only through ace3's API, ace3's own commands run in its dev container, or read-only bind mounts of host directories. It never mounts an ace3 volume, and ace3 sends ace4 nothing.
- **Memory.** Both stacks share one Docker VM (Rancher Desktop on this laptop, 8 CPUs and 32 GB). ace4's defaults run one replica per pool, each with a `mem_limit`.

## Phase 0: workspace and the first build measurement

DESIGN.md names Rust's build time as one of the two results that could change the language pick, so the workspace gets its heavy dependencies before any ACE code.

- [x] **0.1 Workspace.** Create the Cargo workspace with a pinned `rust-toolchain.toml` and `[workspace.lints]` that deny `unused_must_use` and clippy's `let_underscore_must_use`. Done when a scratch crate containing `let _ = fallible();` fails `cargo clippy`.
- [x] **0.2 Dev container.** Add a `dev` Compose service with the toolchain, mold, sccache and bacon, with `target/` on a named volume instead of the macOS bind mount. Done when bacon in the container rebuilds after a save in the host checkout.
- [ ] **0.3 CI.** Run `cargo fmt --check`, `cargo clippy -- -D warnings` and `cargo test` on every push. Done when a formatting error fails CI.
- [ ] **0.4 Layering check.** Cargo rejects cycles between crates, but nothing stops a one-way dependency from the API on an analyzer. Add a CI check over `cargo metadata` that fails when `ace-results`, `ace-api`, `ace-gui` or `ace-search` depends on an `ace-mod-*` crate, directly or through another crate. Done when a scratch dependency from a crate named `ace-api` on one named `ace-mod-x` fails CI. (#1029, #1031, #1066, #843)
- [ ] **0.5 Build-loop spike.** In a throwaway crate, use tokio, axum, sqlx, askama, the AWS S3 SDK and yara-x once each. In the dev container on macOS and on CI's Linux runner, time a clean build, a no-op build, and the path from a one-line edit in a leaf crate to a runnable test binary, five runs each, noting whether sccache was warm. Done when `docs/measurements/build-loop.md` holds both machines' numbers.
- [ ] **0.6 Coexistence check.** `bin/check-coexistence` reads `docker compose config --format json` and fails on anything *Running beside ace3* rules out. That means a project name of `ace`, a host port in ace3's fixed list or one not set from an `ACE4_` variable, an image name that ace3 builds, a `container_name`, an explicitly named volume or network, and the fluentd log driver. CI runs it on every change to a Compose file. Done when CI runs it, and `docker compose up` in ace4 comes up healthy while ace3's default stack is running and ace3's services stay healthy.
- [x] **0.7 No install path.** Nothing assumes where the checkout lives (#920). Done when the stack runs from a checkout moved to another directory.
- [x] **0.8 Local sample set.** Gather the files the comparisons use: ace3's test fixtures, such as the emails under `ace3/tests/saq/modules/test_email/emails/`, and files added by hand. Cover each kind of file the phase 1 and phase 4 modules read: emails, archives (zip, 7z, RAR and password-protected ones), PDFs, Office files with macros, and RTF. Later ports add samples for the files they read. `samples/manifest.json` records each file's sha256, where it came from, its path inside an alert and the meta tags it would carry. Files that didn't come from ace3's repository stay out of git. Done when the manifest covers every kind of file listed here.

## Phase 1: results crate, module SDK and five modules

Track A is the YARA scanner. It holds the other result that could change the language pick, so it starts first, alongside track B. Track C needs 1.23 and 1.24 from track B, and its YARA step needs track A. Phase 1 ends with a decision in 1.32.

### Track A: the YARA scanner

- [x] **1.1 Rule loading.** In `ace-yara`, load a signature directory the way `yara_scanner_v2` 3.0.0 does. Each subdirectory is a namespace. Each rule file compiles alone first, and a file that fails is logged at ERROR with its path and left out. The other files then compile together. Set the default externals `filename`, `filepath` and `extension`, and skip blacklisted rule names. Done when a fixture directory with one broken file loads every other rule and logs the broken file.
- [x] **1.2 Meta filter.** Port the post-scan filter for the five directives in DESIGN.md's table: `meta_tags`, `file_name`, `mime_type`, `full_path` and `file_ext`. A value is a comma-separated list and the rule is kept if any item matches, ignoring case. `!` negates the list, `re:` makes each item a regex search, and `sub:` makes it a substring test. A non-negated `meta_tags` drops the rule when the caller passes no tags. Done when a table-driven test covers each directive with each prefix, plus the no-tags case.
- [x] **1.3 Regex directives at build time.** Compile every `re:` value with the `regex` crate while loading rules, and leave out the rule's file when one fails. Done when a fixture rule with a lookaround in `re:` leaves its file out, with an ERROR that names the pattern.
- [x] **1.4 Rule meta.** Port `ace3/saq/signatures/yara_meta.py`: `enabled`, the rule uuid and `modifiers`. Port `no_alert` as well as `qa`, since `ace3/saq/svs/yara/diff.py` treats both as "never alerts" and DESIGN.md names only `qa`. Done when the cases in `ace3/tests/saq/signatures/test_yara_meta.py` pass as Rust tests.
- [x] **1.5 Scan.** Scan bytes with the externals taken from the file's name and its path inside the alert, the caller's meta tags, the mime type and a timeout. Each match returns the namespace, rule, meta and pattern offsets. Done when a fixture scan returns offsets and a scan past its timeout returns a timeout error, not an empty match list.
- [x] **1.6 Rulesets.** Serialize a compiled ruleset to bytes and key it by hash, with a manifest of the commit, the yara-x version, the files and rules included and the files left out (#1051). A rule directory outside git is keyed by the hash of its sources. Done when two builds of the same commit give the same key. If yara-x's serialization isn't deterministic, key by (commit, yara-x version) instead, and say so in the test.
- [x] **1.7 Mime type.** Compute the mime type with libmagic from a magic database pinned in the image. Done when it agrees with `file -b --mime-type` on a fixture set. Step 1.11 compares it over the whole sample set.
- [x] **1.8 `ace yara scan`.** Add the command to the `ace` binary: scan a file with a ruleset, taking meta tags and a path. Done when it prints the same rules as ace3's `ace yara scan` for three fixture files.
- [x] **1.9 ace3's replay child, with offsets.** `ace3/saq/svs/yara/child.py` records the namespace, rule and meta of each match (`child.py:229`), but not pattern offsets. It imports only the standard library, yara and yara_scanner, so a copy in `tools/ace3/` with offsets added runs on ace3's Python in ace3's dev container. Done when the copy writes offsets for a working directory of local files.
- [x] **1.10 Rust replay child.** `ace yara replay <workdir>` reads a `job.json` in the shape `ace3/saq/svs/yara/replay.py` writes, and writes `result.json` in 1.9's shape. A script in `tools/ace3/` builds that working directory from 0.8's samples, one unit per (file, path inside the alert, meta tags). Done when both children run on the same working directory.
- [x] **1.11 Comparison.** Compile every rule file in ace3's signatures checkout with both scanners, and list the files each one leaves out. That half needs no samples and covers the whole repository. Then run both children over 0.8's sample set at the same commit, and diff the matched namespace, rule and offsets for each unit. Compare libmagic's mime type with `file -b --mime-type` on every sample too. Done when `docs/measurements/yara-compare.md` counts each kind of difference and says how many samples and rules the match half covered.
- [x] **1.12 Triage.** Mark each difference as a yara-x incompatibility, recorded with its rule and the reason, or a port bug, fixed in `ace-yara`. Done when a rerun of 1.11 shows no unexplained difference.
- [x] **1.13 Slowest-rule report.** Enable yara-x's `rules-profiling` feature behind a cargo feature that only the SVS build turns on, and print the slowest rules after a replay. Done when `cargo tree -e features -i yara-x` shows `rules-profiling` for the SVS build and not for the YARA pool binary. Without `-i yara-x` the tree doesn't list a feature that a root feature turns on, so it can't show the difference.

### Track B: results crate, SDK and test harness

- [x] **1.14 Observable kinds.** Dump ace3's observable type names (`ace3/saq/observables/`, with parents from `type_hierarchy.py`) to a JSON fixture, and define the Rust enum from it. Types are an enum, so nothing registers at import (#1030). Done when a test checks the enum against the fixture.
- [x] **1.15 Result envelope.** Define the record every result shares: analysis type name, schema version, details, summary, tags, and the observables and files it adds. Bytes stay bytes. A bytes field serializes to JSON as tagged base64 and never passes through a text codec (#999). Done when a non-UTF-8 byte string round-trips through JSON unchanged.
- [x] **1.16 Registry and schema export.** Register each analysis type by name and version, so finding a type's module needs no instance (#827). `ace schema export` writes each type's JSON Schema with `schemars`. Done when the export of a sample type is snapshot-tested.
- [x] **1.17 Validation.** Check a JSON result against its type's schema. Done when a result with an unknown field or a wrong type fails with the field's path in the error.
- [x] **1.18 Module traits.** In `ace-sdk`, define a sync trait for parsers and an async one for lookups. The task context gives the observable, the settings, the declared secrets, a cancellation token that blocking code can poll (#984, #986), and the time left (#845). A module can return a delay with a `run_after` and a timeout, the counterpart of `delay_analysis` (`ace3/saq/modules/base_module.py:685`). Done when an example module of each kind runs in a unit test.
- [x] **1.19 Manifest.** Each module crate exports a manifest: input observable types, output analysis type, the modules it depends on, resources, sandbox profile, settings schema and secrets. Settings deserialize with `deny_unknown_fields` (#858). Done when a settings block with an unknown key fails to load.
- [x] **1.20 HTTP client.** The SDK gives modules one HTTP client builder that always verifies certificates with rustls (#1018), sets a timeout on every call, and classifies "peer unavailable" errors in one place (#1096). Done when a test against a self-signed server fails and a refused connection is classified as unavailable.
- [x] **1.21 File output.** The SDK writes a new file with its bytes, its name and path inside the alert, and its `yara_meta` tags, through a file store trait (a local directory until 2.5). Names from inside a file are untrusted, so the writer rejects absolute paths and `..` (#829). Done when writing `../../etc/passwd` fails and a normal file records its name, path, tags and sha256.
- [x] **1.22 Spans.** The SDK runs each module call inside a `tracing` span with the root uuid, observable and module. Done when a log line from inside a module carries all three.
- [x] **1.23 Test harness.** `ace-testkit` runs a module on a fixture observable or file without the core, checks the result against its schema, and snapshots it. Done when the example modules from 1.18 have snapshot tests.
- [x] **1.24 Reference dumps.** A script in `tools/ace3/` runs one ace3 module on one sample in the `cli` analysis mode, inside ace3's dev container, and writes its analysis details as JSON. Phase 1 ports compare against these dumps. Done when it writes dumps for the five track C modules.

## Phase 2: the core, the queue and the bucket

The goal is to run the five phase 1 modules end to end from a submission.

### Storage

- [x] **2.1 Postgres and a bucket.** Add Postgres and an S3-compatible bucket to Compose, published on ephemeral host ports. The bucket is SeaweedFS, because MinIO's maintainers stopped publishing community images in October 2025. Done when `docker compose up postgres bucket` is healthy while ace3's stack is running.
- [x] **2.2 Migrations.** Add `ace-core` with SQL migration files and one Postgres schema per area. Commit sqlx's offline metadata in `.sqlx/`, and have CI run `cargo sqlx prepare --workspace --check` against Postgres. sqlx-cli can't check without a database, but building needs none. One function builds the connection pool for every component (#1023). Done when a query on a missing column fails the build.
- [x] **2.3 Test databases.** Migrate and seed a template database once per test run, and give each test its own copy with `CREATE DATABASE ... TEMPLATE`. Done when tests run in parallel on separate databases.
- [x] **2.4 Alert tree tables.** Roots, with an event time and where that time came from (#850). Observables, unique on (root, type, value). Results, unique on (root, observable, module), with the analysis type, schema version and JSONB details under a GIN index. Done when upserting one observable twice leaves one row.
- [x] **2.5 Bucket.** `ace-store` puts and gets bytes by sha256 on S3 (SeaweedFS in dev), with a size-capped cache on each node. A put also stores the libmagic mime type from 1.7. Carry over the pools and retention from `ace3/docs/CAS.md` and the `cas:` section of `ace3/etc/saq.default.yaml`. Done when two puts of the same bytes leave one object and a get on a second node fills that node's cache.

### Queue

- [x] **2.6 Tasks and claims.** A task is (root, observable, module) with a state enum, `run_after`, lease owner and expiry, attempt count, error and input hashes. Workers claim with `FOR UPDATE SKIP LOCKED`. Done when two workers draining 1,000 tasks run each one exactly once.
- [x] **2.7 Leases.** A worker renews its lease while it runs. A reaper requeues tasks whose lease expired and fails a task at its attempt limit. Done when killing a worker mid-task gets the task rerun after its lease expires.
- [x] **2.8 Wakeups.** Workers wait on `LISTEN/NOTIFY`, with a bounded timeout as the fallback. Done when a test shows a task claimed without the fallback firing.
- [x] **2.9 Delays.** A task whose `run_after` is in the future can't be claimed until then. Done when 1.28's delayed module runs again after its delay.
- [x] **2.10 Eligibility.** When a result lands, in the same transaction, find the (observable, module) pairs that just became eligible. A module is eligible when it accepts the observable's type, the modules it depends on have results, the observable's directives allow it (such as `no_scan`), and the root's analysis mode includes one of the module's groups. Modes and module groups carry over from `ace3/etc/saq.default.yaml` (`module_group_*` from line 2537, `analysis_mode_*` from line 2749). When a root's mode changes, eligibility reruns over every observable the root already has. That happens when a detection turns a root into an alert in correlation mode (`ace3/saq/engine/analysis_orchestrator.py:394-398`). A cancelled dependency doesn't fail its dependents forever (#846). Done when a table-driven test covers each rule, and a detection mid-analysis queues the correlation group's modules for the observables already in the tree.
- [x] **2.11 Root completion.** A root is complete when it has no queued, delayed or running tasks, and completion is one event that alert routing can wait for (#848). Done when a test sees exactly one completion event per analysis pass.
- [x] **2.12 Cancellation.** Cancelling a root cancels its queued tasks and signals running ones through their cancellation token. Dispositioning an alert cancels it and then switches it to the `dispositioned` mode, which makes that mode's few modules eligible. Done when a running test module sees the cancel within one poll interval, and a dispositioned alert runs only `alert_added_to_event`.
- [x] **2.13 Transactions.** Every write goes through a sqlx transaction value. `commit` consumes it and dropping it rolls back (#852, #1040). A retry helper reruns the whole transaction closure on a serialization failure, never part of it (#1084). Done when a test forces a serialization failure and the retry reruns every statement.

### Worker API

- [x] **2.14 Lease API.** Axum endpoints for a worker to lease, renew, complete and fail tasks, and to get presigned bucket URLs for its inputs and outputs. A worker then holds neither database nor bucket credentials. Workers authenticate as their pool. Done when a worker with only an API token runs a task end to end.
- [x] **2.15 Result writes.** Completing a task checks the result against its schema, stores it under its analysis type name, upserts its observables, records its files and queues what became eligible, all in one transaction. Done when an invalid result is rejected with the field's path and nothing from it is written.

### Pools

- [x] **2.16 Async pool.** A pool's definition lists its modules, concurrency limit, sandbox profile and secrets, and its container sets the resource limits. `ace-pool` runs many async tasks in one process, up to the concurrency limit, which replaces the `network-semaphore` service. A panic in one task fails that task and the process keeps serving. The process applies 2.18's file and port rules and rlimits before its runtime starts any thread, without the ban on fork and new threads, because tokio needs threads. Done when a pool with a limit of 4 never runs a fifth task while 50 are queued, a panicking task leaves a failed row while the others finish, and a lookup can't connect to a port its manifest doesn't allow.
- [x] **2.17 Task supervisor.** For parser pools, a supervisor starts one process per task by exec, never fork (#982), sends the task on stdin and reads the result from stdout. Setup failures and module failures exit with different codes (#847). Task processes run as a non-root user with no capabilities, which closes 2.18's gaps for raw sockets and for calls on other processes of the same user. Two phase 1 modules start threads, which 2.18 forbids, so both change here. The archive module builds unrar from a patched copy of `unrar_sys` without `RAR_SMP`, because the crate always defines it and unrar then starts a thread per CPU on RAR 5 archives. The YARA module scans without yara-x's timeout when contained, because yara-x starts a heartbeat thread for it, and relies on the CPU rlimit and 2.19's deadline instead. Done when a panicking parser leaves a failed-task row and the supervisor keeps leasing, a task process has no capabilities, and the archive module (on `test.r07`, a RAR 5 file) and the YARA module each run contained.
- [x] **2.18 Containment.** Before the module runs, the task process sets rlimits on address space and CPU time, applies Landlock rules for files and TCP ports, and installs a seccomp filter that blocks fork, clone and exec. A process with no children dies completely when its PID is killed (#981). Done when test tasks that fork, exec, open a file outside their allowed paths, connect to a port that isn't allowed, or allocate past the limit are each stopped, and a task process reports one thread.
- [x] **2.19 Hung tasks.** The supervisor kills a task process at its deadline and writes a failed-task row with the error and the input hashes. Done when an infinite-loop task is killed and its row names its inputs.
- [x] **2.20 Replay.** `ace task replay <id>` fetches a failed task's inputs by hash and runs the module locally, outside containment, so a debugger can attach. Done when replaying 2.19's task reproduces the hang.
- [x] **2.21 Bounded waits.** Wrap every network call, lock and join on a run or shutdown path in `tokio::time::timeout`. Shutdown stops leasing and releases held leases. Done when shutdown with a hung upstream finishes within its deadline and the hung task's lease is released.
- [x] **2.22 Telemetry.** Export spans through OpenTelemetry, with the task id added to 1.22's identifiers. Done when one task's spans appear together in the collector.

### Config

- [x] **2.23 Site overlay.** A small YAML overlay deserialized with `deny_unknown_fields`. A component with no section in it runs on its manifest's defaults (#1044). A module named in the overlay that no longer exists logs a warning, and startup continues (#901, #916). The overlay can also declare named instances of a module, each with its own inputs and settings, the way ace3's `analysis_module_*` sections run many Splunk queries on one class. Each instance is its own task type in the queue, and its results record the instance, so two instances' results on one observable don't collide. Done when tests cover an unknown key, a missing section, a removed module, and two instances of 1.28's Splunk module running different queries on the same observable.
- [x] **2.24 Secrets.** A process resolves only the secrets its pool's manifests declare (#1009). Done when a pool can't read a secret that only another pool declares, and its startup log lists only its own.

- [x] **5.3 Audit.** One helper records the actor on each audited write (#830). Done when every write path in the service layer has an audit test. `Gate::write` takes the function's name as its action and a body that must return `Audited`, either a `Change` or a claim that nothing changed, and the gate writes the row to `service.audit` in the write's transaction, so a failure to record fails the write. `tests/service.rs` reads this crate's source for functions calling `Gate::write` and compares them with what its audit tests compared. ace3's audit is log lines read in Splunk, so this table is new, and `Gate::write` also logs an identity-only line. - [x] **5.4 Authentication.** GUI sessions and API keys. Done when both reach the service layer as an actor. The users table also gives `service.permissions.user_id` and `service.group_members.user_id`, and the keys table `service.permissions.api_key_id`, a foreign key that deletes with the user or key: a grant shouldn't outlive its holder, unlike a row that records an actor. `ace-service`'s `auth` module turns a session token or an API key into an `Actor`, and `Service::authenticate_request` is the call an adapter's extractor makes. Done when 2.30's test gets `phishkit_analyzer` and `javascript_deobfuscation` results through the queue. The Python pool's supervisor, which 4.13 removed, wouldn't have carried them. Each ace3 manager is a Celery worker that does `docker run` of a scanner image per file through the host's Docker socket, and a contained worker dies at its first fork. A worker uncontained enough to fork would leave its scanner running when its PID is killed, and py-spy would only see it waiting on `docker run`. The scanners aren't Python workers either: phishkit's is Chrome under SeleniumBase and needs the network, and js-deobfuscator's is node. So this step needs a pool that leases a task, passes the file to the scanner image and starts it with that image's limits (`--network none` for js-deobfuscator's; memory and CPU limits for phishkit's), removes the container at the deadline, at a cancellation and after a crash of the pool (ace3 labels them and reaps by label), and reads back what it wrote. phishkit's runs for minutes, so it needs a task that waits without holding a slot, as ace3's `delay_analysis` does. Whoever holds the Docker socket has root on the host, so that process parses nothing hostile.

- **The SVS corpus.** DESIGN.md's YARA comparison and library checks over every SVS sample. The samples live in production, not on the laptop.

- **Cutover.** Checking off DESIGN.md's *What it replaces* table.

## Decisions

Made on 2026-10-29, where DESIGN.md left a gap or didn't match ace3.

1. **Analysis modes stay.** A root carries a mode that names its module groups, and a mode change reruns eligibility. DESIGN.md doesn't mention modes. (2.10, 2.12)
2. **Email comes in through a site's journal collector.** ace3 removed its own email collectors in October (`b6e03230`, `754619c6`), so the collector DESIGN.md names is the one in the site_ace integration. (6.1)
3. **extract_msg is dropped.** It has never been in ace3's history. Outlook `.msg` support would be new work.
4. **RAR uses the unrar crate,** in-process inside the contained task. (1.29)
5. **ace4 is a laptop proof of concept for now.** ace3 sends it nothing. Moving data, production traffic and cutover wait until there's a decision to go further. (*Scope*, *Deferred*)
6. **PDFs go through libqpdf.** ace3 never runs qpdf itself; it uses pikepdf, which wraps libqpdf. A Rust module on the qpdf crate replaces pikepdf and `pdf-parser.py`. (4.9)
7. **The API is new.** It keeps no `/api/v2` compatibility. (5.5)
8. **pcodedmp and XLMMacroDeobfuscator go on the Python pool,** pinned, until their ports match, which they did at 4.12, and 4.13 removed the pool. (4.1, 4.7, 4.12, 4.13)
9. **Site integrations live in their own repositories.** site_ace is already its own repository, cloned into `ace3/integrations/` and ignored by ace3's git. Its Rust workspace builds its own `ace` and pool images from this workspace's crates, pinned by tag. ace3 loads integrations as Python packages at run time (#1031); here they are crates linked at build time. (2.31, 2.32, 6.1, 7.8)
10. **Alert routing, detection verdicts and AI query get steps.** DESIGN.md doesn't mention them, but ace3 has them. (7.13, 7.14, 7.15)
11. **ace4's stack runs beside ace3's on one machine.** It takes its own project name, `ACE4_` variables, one fixed host port that ace3 doesn't use, and `ace4-*` image names. (*Running beside ace3*, 0.6, 2.1, 2.29)
12. **Samples come from the laptop.** The local ace3 has no SVS corpus, so the comparisons use ace3's test fixtures and files added by hand. The YARA check compiles the whole signatures repo with both scanners and compares matches only on those files. (0.8, 1.11, 3.3, 4.8)
13. **Other repositories don't change.** Scripts that need ace3's code live in `tools/ace3/` and run in ace3's dev container. The signatures and site_ace repositories stay as they are. (1.9, 1.10, 1.24, 2.32, 3.2)
14. **The comparison follows the newest ace3.** Made on 2026-11-06. `tools/ace3/trees/make-trees` runs on ace3's latest commit rather than a pinned one, and `reference/index.json` records which. A new difference is either ported or listed in `differences.md`. (3.2, 3.3)
