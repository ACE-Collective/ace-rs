# Reads for modules

PLAN.md 7.2. Workers hold no database credentials and no encryption key. A module that reads ACE's own data in ace3 reads it from the core, as its pool, through the lease API (`api.rs`). This file is the contract for those reads, and `reads.rs` beside it serves the ones built. Each module's port step builds the reads it calls, with the tests below, and marks them built here. Built: `snort-signature` (7.4), which brought the endpoint, its replay route, `Module::READS`, `ace_sdk::reads` and `TaskContext::read`; `smtp-counts` (7.4), which brought brocess's `smtplog` (migration 0037); `email-thread-domains` (7.4), with the first writes, `email_logger`'s `smtp-log` and `email-thread`, which brought `Module::WRITES`, `ace_sdk::writes`, `TaskContext::write` and brocess's thread store (migration 0038); `email-thread` (7.4); `newly-registered` (7.4), over migration 0039's newly registered domains list; `archived-email`, `decrypted-archive` and `archived-url-count` (7.5 batch 9), with the `email-archive` write, over the email archive (`email_archive.rs`, migration 0041); and `observable-tags` (7.6), over migration 0042's `analysis.observable_tags`. `writes.rs` beside this file lands the writes.

`docs/modules.md`'s *What 7.2 serves* names what serves each module. `tools/ace3/modules/check` fails when a module that reads ACE's data in ace3 has nothing named there, or names a read this file doesn't have.

## How a module gets ACE's data

In order of preference:

1. **On the lease.** The core adds what it knows when it hands out the task and the module always needs: the carrying email (4.6, `Module::READS_CARRYING_EMAIL`) and the lists the module declares (5.14, `Module::LISTS`). Of the root's own tree, it adds the results of the modules the module depends on (`Module::DEPENDS_ON`), what's below a module that runs last (`Module::READS_BELOW`), which modules added its observable (`Module::READS_ADDED_BY`), its relatives' tags (`Module::READS_RELATED_TAGS`), and, for a module that walks the tree as ace3's walk the `RootAnalysis`, the whole tree (`Module::READS_TREE`, 7.5 batch 8, `ace_sdk::tree`): the root's alert type and whether it's whitelisted, each observable with its tags, directives, paths and their `yara_meta`, how many detections it has and the modules with a task on it still to finish, and each result by module and analysis type with what it added, at most 20,000 of each, cut in the order they were added and said so. A file of the tree whose bytes the module reads (`Module::READS_TREE_FILES`: by part of its name, up to a size) comes with a presigned download, which the pool fetches before the task runs. A module that walks the tree hands back what it changes elsewhere in its result, and only what it declares, since a parser's result comes from hostile input: additions to other observables in the root (`ResultEnvelope::others`), limited to the tags and directives, and detections or not, its `Module::ADDS_TO_OTHERS` names, so the core rejects the result for any other addition, any `yara_meta`, or any `others` from a module that declares nothing (the lure module declares `crawl`, the mailbox module `tracked`); and, for one that declares `Module::SETS_ROOT`, the root's description and details (`ResultEnvelope::root`), which the core refuses from any other. A refused result fails its task with the reason, as one that fails its schema does.
2. **On the ruleset** (`GET /api/worker/v1/yara/ruleset`), for data that changes with the rules.
3. **A read**, `POST /api/worker/v1/tasks/{id}/reads/{read}`, for something the analysis decides, such as a Message-ID or a URL. Only a lookup pool's module calls one. A parser's task process has no network and no channel back to its supervisor while it runs, so a parser gets its data on the lease or the ruleset.
4. **A write lands with the task's end** (`POST /api/worker/v1/tasks/{id}/end`). It goes in the end's own transaction, so a task that's retried never writes twice and a failed one writes nothing. The module declares its writes in `Module::WRITES`, and `TaskEnd::Done` carries them beside the result, or `TaskEnd::Skipped` with no result, as for a module that stores none (*The write contract*).

## The read contract

A module declares its reads in `Module::READS: &'static [Read]`, where `ace_sdk::reads::Read` names each read, as `LISTS` names lists. The manifest carries the list. `Manifest::parser` refuses a parser that declares one, so such a module's `MANIFEST` constant doesn't build, and no catalog can hold it. The module calls a read with `TaskContext::read::<R>(&request)`, typed by the read's `ace_sdk::reads::ReadKind` (its request and answer), which goes through the pool's client with the pool's token (`ace_pool::client::TaskReads`). In tests, `ace_testkit::reads::FakeReads` answers instead, through `Harness::reader`.

The request is `POST /api/worker/v1/tasks/{id}/reads/{read}`, with `Authorization: Bearer <pool token>`, the worker's name in `x-ace4-worker`, and a JSON body. The answer is JSON. The core checks, in this order:

| Status | When |
|---|---|
| 401 | the token isn't a pool's |
| 400 | no worker header, or the body doesn't read |
| 409 | the task isn't leased to `<pool>/<worker>` now: another pool's token, another worker of the same pool, a task that ended, or a lease past its `lease_expires_at`. `Worker::owned` alone doesn't check the expiry, so a read also checks `lease_expires_at > now()` |
| 403 | the task's module doesn't declare the read, or the request names an observable or file that isn't in the task's root |
| 503 | the store behind the read is down. ace3's thread analyzer goes into cooldown when brocess times out, and the port does the same on a 503 |
| 200 | the answer. Nothing found is a 200 with an empty answer, not a 404, so a module can tell a miss from a refusal |

**Scope.** Each read names its subject: the task's own observable, or an observable or file in the task's root. A request's `subject` (`{"type", "value"}`) names an observable; left out, it's the task's own. The core looks the subject up by root and type and value, or by root and sha256, before it reads anything. Most reads answer only about that subject. Some answer from other alerts' data, as ace3's do. Those are marked in the table below with their bound: a count, or capped rows of header metadata. None returns another alert's tree, its files or its id.

**Sensitive data.** The core decrypts with ACE's key, `ACE4_ENCRYPTION_KEY`, and the key never leaves the core (`ace serve`). A read that yields an email (`archived-email`, `decrypted-archive`) puts the plaintext in the bucket's `alert_files` pool, held by the task's root, as a module's own output file is, and answers with the file's sha256 and size. A lookup pool can't reach the bucket, so the module adds the email to its result by those as a `NewFile` with no upload: the pool uploads only the files it has, and the core takes a result's file with no upload only from a module that declares one of these reads (`ace_sdk::reads::FILE_READS`) and only when the root holds it; otherwise it refuses the end as it refuses any result naming a file that wasn't uploaded (400), nothing lands, and the task stays the worker's. The same goes for a file another result stored for the root without adding it (`ResultEnvelope::stored`, as pcap_analyzer stores what it carves, 7.5 batch 13): the core takes it with no upload only from a module that declares `Module::ADDS_STORED_FILES` and only when the root holds it. A file taken with no upload gets the bucket's size, whatever the result says, since a module that didn't upload it may not know it. ace3 doesn't audit these reads: its `log_audit` records its API's callers, and its modules' archive reads write only their own log lines. So ace4 writes no audit row for them either. The core logs each with the task, the root, the read and the sha256. A person's read of the archive, through the `email` router, is audited (`ace_service`'s `email_archive` docs).

**Replay.** `ace task replay` replays a task without a lease. A replayed module calls `/api/admin/v1/tasks/{id}/reads/{read}` with the admin token, with the same checks except the lease (`LeaseClient::replay_reads`). Built with `snort-signature`.

**Tests.** When a read is built, it gets tests for a success, an unknown token (401), another pool's token (409), another worker (409), an expired lease (409), a subject from another root (403), a module that doesn't declare the read (403), and its bound: an answer past its cap says it was truncated. `snort-signature`'s, `smtp-counts`', `email-thread-domains`', `email-thread`'s, `newly-registered`'s, the archive's three and `observable-tags`' are in `crates/ace-pool/tests/lease_api.rs` (`assert_refusals` makes the shared ones for each), through the pool's client, with a body that doesn't read (400), a store that's down (503), the replay route with and without the admin token, and the snort, frequency, logger, thread, newly registered domains and user defined tagging modules run as the lookups pool runs them; `snort-signature` has no bound, answering one rule line, nor has `newly-registered`, answering a yes or no about the task's own observable, which answers each value of ace3's `nrd_analyzer` dumps as ace3's list did and refuses any other subject, even one in the task's root (403). `email-thread-domains` and `email-thread` are also replayed over ace3's thread dumps, which each answers as ace3 did; the first refuses a subject no email in the root has and more than 100 domains (403), and the second a subject that isn't a message_id (403). `observable-tags` answers each observable and file of ace3's `user_defined_tagging` dumps with the tags ace3's database gave it, refuses any subject but the task's own observable (403), and past 1,000 tags answers the first 1,000 and says it cut them. The archive's three answer only for the task's own observable and refuse a sibling in its root (403): `archived-email` and `archived-url-count` answer each Message-ID and URL of ace3's dumps as ace3's archive did, over the same emails seeded in Postgres and the bucket (`EmailArchive::seed`), the newer of two archives, an object gone as an error, an empty email as one of 0 bytes; `decrypted-archive` opens each sealed fixture ace3 opened to the same email, answers the rest (another key, a changed byte, a truncated file, a body that isn't gzip) with an error, refuses a file not named `.gz.e` (403), and answers a core with no key with an error. Their bound is the 64 MiB the core opens (`email_archive::MAX_EMAIL_BYTES`), past which the answer is an error. The opener and the Message-ID module run as the lookups pool runs them, adding the email with no upload; a result that adds a file no read put in the root, or that comes from a module that declares no such read, is refused as a missing upload is. A write, when it's built, gets tests that it lands with its end and is refused (403 and 400, failing the task with nothing written) as *The write contract* says, that a lost lease writes nothing, and its bound; `smtp-log`'s and `email-thread`'s are in the same file, which also replays ace3's thread dumps through the core's writes and checks brocess against what ace3 left, hashes and all. `email-archive`'s is there too: the archiver run through the pool on each email ace3 archived leaves ace3's rows (the hash, the Message-ID's and each URL's index, each recipient), the result's `archive_id`, and the sealed email held past retention; and it's refused from an undeclared module, with a body that doesn't read (400), about another Message-ID, past 1,000 recipients, twice in one end, or on a core with no key (403), and a lost lease writes nothing.

## The write contract

A module declares its writes in `Module::WRITES: &'static [Write]`, where `ace_sdk::writes::Write` names each, as `Read` names a read, and `Manifest::parser` refuses a parser that declares one. The module makes one with `TaskContext::write::<W>(&body)`, typed by the write's `ace_sdk::writes::WriteKind`. Nothing goes to the core then: the context keeps the task's writes, and the pool sends them with the task's end when that end is a result (`TaskEnd::Done`) or a skip (`TaskEnd::Skipped`). It drops them with any other end, so a task that fails, delays or is cancelled writes nothing. In tests, `Harness::run_lookup_writing` returns them beside the outcome.

The core checks them before the end's transaction, after the checks every end makes (401, 400, 409 for a task not leased to the worker). A refused write fails the task with the reason in its row, as a result that fails its check does, since the module would write the same on another attempt, and nothing of the end lands:

| Status | When |
|---|---|
| 403 | the task's module doesn't declare the write, the write is past its bound, or it's about another email than the task's own observable's |
| 400 | a write's body doesn't read |

Then the writes go in the transaction that ends the task: with the result, for a `Done`, or with the task's end alone, for a `Skipped`. A second end of the same task is refused (409) and writes nothing more. ace3 audits none of these writes, so the core writes no audit row for them either; it logs each with the task, the root and what it wrote.

## Served another way

- `yara_scanner_v3_4`, **on the ruleset**. ace3 reads the `observable_detections` row a matched `$obsd_<id>` string names, and adds its observable. In ace4 those rows are entries of 7.6's `observable_detection` list (5.14). The export is to write their rules, and the ruleset the core builds to carry each `$obsd_` id's observable type and value beside the rules, both from one read of the list, so a rule and its observable always agree. ace3 reads the row at scan time and skips one deleted since the export. ace3's legacy `$obs_<id>` strings name its own `observables` rows, which ace4 doesn't have, so they aren't served (`crates/ace-mod-yara/tests/differences.md`). Not built: 7.6 built the list, its router and its page, and the export waits (PLAN.md 7.6).
- `observable_detection`, **on the lease**: the `observable_detection` list in `Module::LISTS` (7.6, built). ace3 reads a Redis copy that `ace observables export` keeps.
- `alert_added_to_event`, **in the core**. Its pool is the core's, since it changes the root's analysis mode, so it reads the root's events there. The owner hasn't decided whether it's ported.
- **Writes, at the task's end** (*The writes*). `email_archiver` archives the email: its sealed copy in the archive's pool, held by its row, its archive, index and history rows, and once the root's analysis is done, the index of the URLs below it (built). `email_logger` adds to brocess's `smtplog` and records the thread (built). `svs_yara_sample_capture` records its captures and SVS's holds.
