# Differences from ace3's reference dumps

`tests/reference.rs` runs the user module on each user and email address `tools/ace3/dumps/reference/user_analyzer/` has a dump for. ace3 asked `tools/ace3/dumps/fake_ldap.py`, which served `tools/ace3/dumps/fixtures/ldap/directory.json` in plaintext on 127.0.0.1, as ace3 binds; the test asks `ace_testkit::ldap`, which serves the same directory the same way, with `allow_plaintext` set as an overlay must set it for plain LDAP. The directory's schema gives each attribute AD's syntax, with test attributes for the syntaxes AD's users don't carry, so the dumps show ldap3's formatting of DN, directory string, OID, telephone number, integer, large integer, boolean, octet string and generalized time values, AD's GUID, SID, timestamp and interval attributes, RFC 4530's UUID, single and multiple values, a value that isn't UTF-8, values a formatter can't read, and an attribute the schema doesn't have. The test also checks that each run's searches under the base are the ones ace3 made, word for word, paged as ace3 paged them. Both results go into the normal form `ace_testkit::reference` describes, and the test fails on any difference this table doesn't list, or on a row that no longer matches anything. The dumps were made with ace3 at commit 85c8e9e5.

## Behaviour the dumps don't exercise

These depart from ace3:

- **The connection.** ace3 binds with its password in plaintext on port 389 (`ldap_server`, `ldap_port`). The module's `server` is an `ldaps://` URL, or an `ldap://` one that it upgrades with StartTLS before the bind, and it verifies the server's certificate against the platform's roots and `ca_certificates`. Plain LDAP needs `allow_plaintext: true`, which logs a warning when the module starts. `tests/reference.rs` shows LDAPS and StartTLS against `ace_testkit::ldap`, a certificate nobody vouches for refused before any bind, and a server without StartTLS refused unless plain LDAP is allowed.
- **Waits.** ace3's ldap3 sets no timeout. The module waits at most `connect_timeout_seconds` (10) to connect and `operation_timeout_seconds` (30) for each operation, and a search reads at most 100 pages.
- **The connection's life.** ace3 keeps one connection a process, restarting it when it drops (ldap3's RESTARTABLE strategy). The module connects and binds for each task and keeps the schema for the process.
- **Failures.** A directory that can't be reached, or an operation that fails, fails the task as unavailable, so it runs again later; a bind the directory refuses fails the task. ace3's RESTARTABLE strategy retries, and then the module raises.
- **The schema.** ace3's ldap3 reads the root DSE's and the schema's every attribute (`get_info=ALL`); the module reads `subschemaSubentry` and `attributeTypes`, which is all the formatting uses. A server with no schema gives every value as text and every attribute as a list, as ldap3 does without one. ldap3 also finds a formatter by the names its own OID table gives an attribute's OID, which reach only the table's two name keys (`supportedldapversion` and `octetstring`); that lookup isn't ported. An integer past 64 bits is written as text, where ace3 writes the number.
- **Referrals.** ace3's paged search lists a search result reference beside the entries, and with an AD domain's base the reference is what its reversed page puts first, so `entries[0]['attributes']` raises. The module skips references. The fake serves none.
- **Unexpected values.** Where ace3 raises on an entry, the module fails the task with the same reason: a `manager` that isn't one DN starting `CN=`, an `msExchRecipientTypeDetails` that isn't an integer, or a `cn` that isn't one value for an email address. A `mail` that isn't one value adds no address, where ace3 raises.
