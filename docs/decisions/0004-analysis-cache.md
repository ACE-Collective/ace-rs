# 0004: A cache of module results across alerts

Status: decided on 2026-11-18 and built the same day (PLAN.md decision 26; *As built*, below). The owner decided that day that ace-rs needs a version of ace3's analysis result cache, and accepted this design's four choices: the cache is checked before a task is queued, so a hit makes no task; the comparison runs with the cache off, plus the two-run check; ace3's seven opt-ins and their times to live are ace-rs's defaults; and the time to live is a setting in the overlay, per module. It replaces PLAN.md 6.7's "ace-rs has no analysis cache".

## Why

The same thing turns up in many alerts: the same image in a hundred phishing emails, the same domain in a week of hunts. ace3 runs a module once on it and reuses the result in later alerts for a time the module's config sets (`cache_ttl`). The owner's figure: hundreds of hours of compute a day saved in production, from OCR and QR code alone. For a site's lookups it also spares vendor quotas.

ace-rs has nothing like it. Decision 15's "one analysis per file" holds inside one root only: the next alert with the same file runs every module on it again.

## What ace3 does (`ace3/docs/ANALYSIS_CACHING.md`, at `fe6da632`)

- **Opt-in per module**, with a time to live: `rdap_analyzer` 7 days, `nrd_analyzer` 24 hours, `site_tagger` 30 days, `ocr` 7 days, `qrcode` 7 days, `phishkit_analyzer` 6 hours, `pdf_link_text` 30 days. A global switch stops all writes.
- **The key** is a sha256 over the observable's type and value, the module's name and version, a hash of its config (less operational fields), and an *extended version*: what else the output depends on, such as tesseract's version for OCR or the content hash of a list file for `site_tagger`.
- **What is stored** is the module's *delta*: the analysis it made, the observables it added (files by content, in a blob store), and what it added to the observable it analyzed. Most of ace3's design is about finding that delta, because an ace3 module edits the tree in place and nothing records which module did what.
- **Never cached:** a failed analysis (`Analysis.error`), a module that hasn't finished (a delay), a result that removes anything or touches observables other than its own and its new ones, a delta over 1 MiB.
- **A hit** replays the delta into the new root as if the module had run, and is recorded as a hit. Expired rows are dropped by daily partitions.
- **Not cached on purpose:** YARA, whose output depends on the file's name and `yara_meta`, which the content key doesn't see.

## The design for ace-rs

**What makes it simpler here.** An ace-rs module doesn't edit the tree. It returns one result envelope, and the core applies it: its details, summary, tags, detections and the observables and files it adds, each addition recorded against the result (`analysis.result_additions`). The envelope *is* the delta. Files are already stored once by content in the bucket. So ace-rs caches the envelope and the sha256s of its files, and a hit applies that envelope through the same path as a task's end.

**A module opts in** with `Module::CACHE`: whether it may be cached, and what its extended version is (a function of its settings and its tools' versions, as decision 23's declarations are built from its settings). The time to live is a setting in the overlay, per module, so a site sets it as ace3's config does, and the global switch is a setting too.

**Only a module whose output depends on nothing but its key may opt in.** A module's lease says what else it reads: dependencies' results (`DEPENDS_ON`), the tree (`READS_TREE`, `READS_ADDED_BY`), the carrying email, its path or `yara_meta`. A pool refuses to start with a cacheable module that reads any of them, unless what it reads is part of its key. This is the rule ace3 enforces with a contract lint, made a check the binary can't skip.

**The key** is a sha256 over: the cache's format version; the observable's type and value (a file's value is its sha256); the module's name, version and instance; a hash of its settings, less the time to live; and its extended version. Under docs/decisions/0003 a file's type facts follow from its sha256, so they need no place in the key; its role does not, so a module whose output depends on the role must put it in its key or not opt in.

**Where the cache is checked: in the core, before a task is queued.** When eligibility would queue a cacheable module's task, the core looks the key up first. A hit writes the cached envelope as that module's result on the observable, records it as a hit, and queues no task: no lease, no pool, no process. A miss queues the task as now, and its end writes the cache when its result may be cached. One indexed lookup per would-be task of an opted-in module, and none for any other module.

**Never cached:** a result with `error` set (decision 19); a task that failed, timed out or was cancelled; a delayed task until its final run, and then the final envelope only; a result that adds to anything but its own observable and the observables it creates; an envelope larger than a limit (ace3's 1 MiB, compressed).

**Storage: Postgres and the bucket, nothing new.** A table in its own schema, `cache.results`: the key, the module, the observable's type and value, the envelope as `jsonb` (Postgres compresses large values itself), the files' sha256s, `created_at` and `expires_at`. The newest unexpired row for a key wins, as in ace3. Each row holds its files in the bucket, as a root does today, so the bucket's collector doesn't remove a file a cache row still names. Expired rows go by daily partitions, dropped by a scheduled task (7.12's scheduler), with the retention longer than the longest time to live.

**What a person sees.** A result from the cache is the module's result, shown and returned as any other, with a mark saying it came from the cache and when the original ran (ace3's `from_cache_hit` and `cached_at`). The metrics event's module records (decision 24) count hits and misses per module, as ace3's do.

## The comparison with ace3

`tests/e2e/run`'s comparison runs with the cache off, so every sample is analyzed live and the comparison checks the modules, not the cache. A new check in the same run turns the cache on and runs a set of samples twice: the second run must take its cached modules' results from the cache, run none of their tasks, and give the same normal form as the first. That is the proof a hit is equivalent to a run.

## Expected effect

On the laptop's comparison it saves nothing, by design. In production it saves what ace3's saves, for the same modules: the owner's figure for OCR and QR code is hundreds of hours a day. With ace-rs's other costs gone (decisions 21 to 23) a cached module costs one indexed lookup and one result write where it cost a contained process and its tool. The step measures a hit's cost and a run's on the 14 large samples, run twice with the cache on.

## In what order

1. The cache itself (opt-in, key, the core's check, storage, the bucket holds, expiry, the mark, metrics), with ace3's seven opt-ins, and the two-run check in `tests/e2e/run`.
2. A site's cacheable modules opt in as they are ported (the site's own `docs/modules.md`, question 9).

Not now: ace3's designed-but-unbuilt *single flight* (two alerts with the same new file at the same moment both run the module; the second could wait for the first).

## What the owner decides

1. Whether the cache is checked before a task is queued (no task on a hit), as proposed, or at the lease.
2. Whether the comparison runs with the cache off plus the two-run check, as proposed.
3. Whether ace3's seven opt-ins and their times to live are ace-rs's defaults.
4. Whether the time to live lives in the overlay per module, as proposed.

## As built

**The opt-in** is `Module::CACHE`, an `ace_sdk::cache::Cache`: a `version` raised when the module's code would answer differently, a default time to live, how the files it adds are named (`CachePaths`), and its extended version: the analyst-edited lists it reads, the programs it runs, files of its pool's image, libraries linked into it, and the reads of ACE's data whose answers the core can make (`KEYED_READS`, only `newly-registered` so far). A module ace3 can cache but doesn't by default has a time to live of zero, kept only once the overlay gives it one.

**The key** (`ace_sdk::cache::key`) is a sha256 over each part as `label:length:bytes` under a format version: the observable's type and value, the module's name and instance, `Cache::version`, its analysis type and schema version, a sha256 of its settings block in canonical JSON, and the extended version, each as `list:`, `tool:`, `file:`, `library:` or `read:` with its value. A list is the sha256 of its entries that haven't expired; a tool, the first line its version arguments print (`ToolSpec::version_args`); a file, the sha256 of its bytes; a library, what the module says; a read, its answer for the observable. The pool reads the tools, files and libraries once when it starts (`ace_pool::cache`) and sends them with each result (`TaskEnd::Done::probes`); a result is kept under the versions its pool sent, and the core keeps the last ones (`cache.probes`) for its lookups. Until a task of the module has ended with them, a module that needs them has no key and nothing is looked up. The time to live is beside the settings in the overlay (`cache_ttl`), not in them, so changing it keeps what was kept.

**The refusal rule** (`ace_sdk::cache::refusal`, `Manifest::cache_refusal`): a cacheable module can't read its dependencies' results, its tree, which modules added its observable, its carrying email, its related observables' tags, what is below it or the rules that matched there, a list, tool or read its key doesn't hold, or a read the core can't key; nor write ACE's data, add to other observables, change its root, add stored files or send its observable through a scanner whose image its key doesn't hold (`Cache::scanners`, since 2026-11-19). A fact only its declaration reads is no refusal (PLAN.md decision 27). Every binary refuses such a module with a `cache_ttl` when it reads its overlay (`Overlay::components`), so no pool starts with one, and `ace`'s own test checks every manifest. A parser's lease also carries its file's path, `yara_meta` and role, which no declaration names: a cacheable module's result may depend on its path only through the paths of the files it adds, which it declares as a function of the path it read (`CachePaths::Named`), and a kept result names each file by its place in that list.

**The check before queueing** (`Orchestrator::queue_eligible`, `try_hit`): where eligibility would queue a cacheable component's task, it gathers it, queues everything else first, then looks each up in the same transaction. A hit writes the kept envelope as the component's result through the same code as a task's end (`apply_result`: details, summary, tags, detections, the observables and files it adds, the hooks' rules over what it touched, and what becomes eligible), marked `analysis.results.cached_at`, holds its files for the root, and queues no task. A miss queues the task. A kept result that adds files needs the file's analysis path (decision 15), so it is settled first, as a lease would settle it; when a lease would still hold the file for its path, the task is queued, and its lease, once the path is settled, looks the key up again and ends the task with the kept result, with nothing sent to a pool (`Api::land_kept`), as a type step whose bytes were typed before ends there. The same lookup at the lease finds what another root kept after the task was queued. A task's end keeps its result (`Orchestrator::keep`) in its own transaction.

**What is never kept** (`ace_core::cache::refusal`): a result with `error`; a task that failed, timed out, was cancelled or ended skipped, since only a `Done` end lands a result; a delayed task's runs before its last, which end with a delay and not a result; a result with `others`, `redirected`, `root` or `stored`, or with writes; one that adds a file at a path its module doesn't name after its input, or any file from a module that names none; and one past 1 MiB deflated. **Amended on 2026-11-22** (PLAN.md decision 47): nor a result its module returned as `Outcome::DoneNotKept`, an answer that holds only for now, such as VirusTotal not knowing a hash, which ace3's VirusTotal module never put in Redis; it lands in its root as any result does. ace3's negative results follow from the modules: qrcode and ocr return a result for a clean scan and skip one that failed, as ace3's record a summary-less analysis and nothing. phishkit isn't cacheable here (below), so its timeouts aren't kept.

**Storage and expiry.** Migration 0072's `cache` schema: `cache.results` (the key, the component, the observable's type and value, the envelope as `jsonb`, each file's place among its module's paths and its sha256, `created_at`, `expires_at`), partitioned by day on `created_at` with a catchall that stays empty, primary key `(key, created_at, id)`, so a lookup (`expires_at > now()`, newest first) is one index range. Each row holds its files in the bucket as a hold `cache`, `<row id>` that expires with the row, so the bucket's collector keeps them while the row lives and lets them go after, with no release; a hit holds them for its root as a task's end does. The scheduler's `analysis_cache_partitions` task, daily as ace3's `ace partitions maintain`, drops each day `retention_days` (35) after it ends and makes the days to three ahead; the core refuses to start with a time to live as long as the retention. `cache.probes` holds the pools' versions and `cache.activity` the counts for the metrics. Costs: a lookup is one indexed read and, for a module with lists, one read of its list's entries; a keep is one insert and a hold per file; a hit is the result's own writes. Rows are never updated or deleted one by one.

**What a person sees.** The GUI's tree marks a result from the cache with a `cached` badge whose title says when the run it was kept from ended, and its page says so above the details. The API's result has `from_cache_hit` and `cached_at`, ace3's names. A pass's module events (decision 24) carry, for a module the cache did anything for, ace3's `cache_hit_count`, `cache_miss_count`, `cache_write_count_insert`, `cache_write_bytes_compressed_sum`, `cache_lookup_ms_sum` and `cache_lookup_ms_max`; a module whose every result came from the cache has an event with no runs. A lookup at a lease counts its hit; its miss was counted when the task was queued. ace3's `cache_lookup_key_ms_sum` and the other component sums, the write latency and the 15-minute `cache_stats` heartbeat aren't filled.

**The opt-ins**, ace3's at `fe6da632` (`etc/saq.default.yaml`): `qrcode` 30 days (pdfinfo, gs and zbarimg's versions, OpenCV's, the `qrcode_filter` list); `ocr` 30 days (tesseract's version, and here also the en_US dictionary's bytes and OpenCV's version); `pdf_link_text` 30 days (pdftotext's version); `rdap_analyzer` 7 days; `nrd_analyzer` 24 hours (the list's answer for the observable, where ace3 keys on its database file's version); and `site_tagger`, whose key is its settings, kept only with an overlay `cache_ttl`, since ace3's default config gives it none. This differs from the list in *What ace3 does* above, which was ace3's design document's table: at `fe6da632` ace3's config keeps `ocr` and `qrcode` 30 days, not 7, and doesn't keep `site_tagger` by default. `phishkit_analyzer` wasn't cacheable as first built: its lease carried its tree (for the mode, which only its declaration reads) and file_type's result (likewise), which the refusal rule refused because it couldn't tell a read only a declaration makes from one the result depends on; and its result is the scanner's run, whose image the key has to hold, as ace3's `scanner_image` does. **Amended on 2026-11-19** (PLAN.md decision 27): a fact only a declaration reads comes in the lease's gate, which `analyze` never sees, so it is no refusal; phishkit's declaration reads the mode there and the file's type for the mime type, and it no longer depends on file_type; the scanner pool reads each scan's container's image id from Docker and the key holds it (`Cache::scanners`, `queue.scans.image_id`, migration 0076), as a tool's version is held; its files are under a directory named after the observable (`CachePaths::Under`). It is kept for ace3's 6 hours. As in ace3, a file's result is keyed on its bytes alone, so a hit for a file in another alert names the first file's path in `scan_result`.

**qrcode's declaration.** The module ran on every file and skipped those that aren't images or PDFs, so a lookup was made for each, as ace3's did until its 2026-06-25 consult gate. Its declaration now takes only an image Pillow opens or a PDF, by the file's type: the type step records Pillow's identification as `is_image` (migration 0073, `ace_mod_files::pillow`), the module's own test, moved there from `ace-mod-sandbox`.

**Where ace-rs departs from ace3's rules, and why.** ace3 finds a module's delta by diffing the tree around its run, and so refuses removals and checks relationships' scope at write time; an ace-rs result is the delta, and the refusal of `others`, `redirected` and `root` is the scope rule. ace3 spills large details to its blob store and keeps file bytes there; ace-rs keeps the envelope as `jsonb`, which Postgres compresses, and a file is already in the bucket by its sha256. ace3 replays a file at the path it had in the first alert; ace-rs names it after the new root's path. ace3's key for `nrd_analyzer` is the database file's version; ace-rs's is the list's answer for the name, which changes only when the name's listing does. ace3 probes each node's tools at each key; ace-rs's pools probe once when they start, and a result is kept under the versions of the pool that made it. ace3's `single flight` stays unbuilt, but the lookup at the lease catches a result kept while a task waited.

**The comparison and the two-run check.** `tests/e2e/site/overlay.yaml` turns the cache off, so the comparison checks the modules. `tests/e2e/run`'s two-run check, after the comparison, runs nine samples once with the cache off, as a control, then twice with it on (`CACHE_SAMPLES`): every result of a cacheable module the first cached run kept must come from the cache the second time with no task of it run in a pool, what it couldn't keep (a result with an error, a task that ended with none) runs again, and each sample's normal form must be the same wherever the control and the first cached run agree, with files named by their paths. Two runs of a sample differ without any cache: ExifTool reports the file's times on the disk, and Ghostscript's rewrite of a PDF has new bytes, so a new sha256, every run, which the comparison with ace3 lists in differences.md. `ocr` runs on no sample.

**Measured** in `docs/measurements/analysis-cache.md`: on the 14 large samples a warm run takes 23 of 6,309 results from the cache, about 100 fewer tasks, with time and CPU the same within the spread, since those samples are made of modules that don't opt in; a lookup costs 0.16 to 0.6 ms of the core's time on average where a qrcode run held a sandbox slot a median 178 ms.
