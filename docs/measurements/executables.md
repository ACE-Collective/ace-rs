# The unpackers and decompilers on crafted files

PLAN.md 7.5 batch 11: `java_class_decompiler`, `upx`, `autoit`, `de4dot` and `ilspy` on files made to cost them most, contained, as a pool runs them. Measured on 2026-11-10 in ace-rs's dev container (Rancher Desktop, Linux 6.18, aarch64, 10 CPUs) with `ACE_RS_CRAFTED=<dir> cargo test -p ace-pool --test hung_tasks crafted -- --ignored --nocapture`, which runs `test-pool parsers --task-user ace-rs-task --concurrency 1` and gives each file to the module its name starts with; one run each, debug builds of the pool, the time from the task's queuing to its root's idle. `tools/samples/make-executables-hostile DIR` writes the files.

Each module's task has ace3's `maximum_analysis_time`, 60 s; the runner gives each run the module's timeout (CFR 30 s, de4dot and ilspycmd 10 s, as ace3), or for upx and unautoit, which ace3 gives none, the task's time left less 5 s. Every tool has the runner's limits: 4 GiB of address space (12 GiB for .NET, ace3's, with its 1 GB heap limit), CPU seconds of the timeout times the cores, a 1 GiB file size, 1,024 open files, 64 MiB of stdout and of stderr.

| Module | File | What it does to the tool | Ends | Time |
|---|---|---|---|---|
| java_class_decompiler | `branches_4600.class`, 32 KB: one method of 4,600 blocks, each branching to one picked at random, as many as 16-bit offsets reach | CFR's structuring takes superlinear time: 3,000 blocks take it 14 s plain, these 34.9 s, and then it gives up on the method | done, no source; `stopped`: `cfr did not finish: it ran past its timeout` | 30.5 s |
| upx | `zeros_400mb.exe`, 612 KB: a PE file of 400 MB of zeros, packed by the image's upx | unpacks to 400 MB. upx won't pack a larger one (`CantPackException: mem_size`, past about 512 MiB), so no UPX file unpacks past the runner's 1 GiB | done, the 400 MB file added, as ace3 adds it | 3.6 s |
| autoit | `scan_400mb.exe`, 400 MB: a PE file with AutoIt's marker and no AutoIt header | libautoit looks for its header under each of 256 XOR keys, a pass over the whole file each: `list` takes 36 s and says `Script not Found` | done; `error`: `unautoit extract-all timed out`, the second run cut at the task's time left | 55.4 s |
| autoit | `alloc_4gb.exe`, 834 KB: ace3's hello_autoit.exe with one resource whose decompressed size field says 4 GiB | libautoit allocates that as it lists the file | done, no scripts; the listing's `stderr` holds Go's `runtime: out of memory: cannot allocate 4294967296-byte block`, the 4 GiB address-space limit | 0.6 s |
| de4dot | `methods_300k.exe`, 12 MB: 300,000 small methods, written by System.Reflection.Emit | detected as an unknown obfuscator in 2.9 s; the clean ran out of its 1 GB heap at 7.3 s plain (`OutOfMemoryException`) | done; `error`: `de4dot did not finish: it ran past its timeout` | 13.9 s |
| ilspy | `nops_70m.exe`, 70 MB: one method of 70 million nops | ilspycmd writes its IL at 150 MB/s, 1.1 GB of it | done, no file; `stderr`: `ilspy did not finish: it wrote a file larger than allowed` (SIGXFSZ at 1 GiB) | 6.8 s |

Every run ended inside its limits, with why in the result. Where ace3's module only logs a tool it stopped (`java.py`), the port's result has `stopped`; where it records `did not finish` (`upx.py`, `dotnet.py`) or `timed out` (`autoit.py`), the port adds the runner's reason.

What the first run of these found, and what changed:

- Every .NET file System.Reflection.Emit wrote made `de4dot -d` abort at once under the runner, `No usable version of libssl was found`: its references carry public keys, which dnlib hashes to tokens, and .NET hashes with OpenSSL, which it loads by dlopen and Landlock refused. de4dot's spec now reads `libssl.so.3` and `libcrypto.so.3`, and nothing more (`crates/ace-pool/tests/containment.rs`, `de4dot_reads_openssl_to_hash_a_public_key`; `samples/ace-rs/executables/emitted_methods.exe` is such a file).
- CFR couldn't start as the task's user: `ADD --chmod=644` had given CFR's directory in the image that mode too. The jar is installed with `install -D` now, and `crates/ace-pool/tests/hung_tasks.rs`' `the_executable_modules_run_their_tools_as_the_task_user` runs all five tools as the task's user on every test run.
- The dev stack's bucket, SeaweedFS under its 1 GiB `mem_limit`, was OOM-killed taking the crafted inputs and upx's 400 MB output (it peaked at 984 MiB with 3 GiB allowed), and the tasks then waited for it. The measurement ran with `ACE_RS_BUCKET_MEM_LIMIT=3g`. A 400 MB unpacked file is a real output of a 612 KB attachment, so the bucket's memory under large files is for the owner; nothing here changes it.
