# The macOS image modules on crafted DMGs

PLAN.md 7.5 batch 12: `dmg_analyzer` and `cve_2021_30657_analyzer` on DMGs made to cost dmg2img and 7z most, contained, as a pool runs them. Measured on 2026-11-10 in ace-rs's dev container (Rancher Desktop, Linux 6.18, aarch64, 10 CPUs) with `ACE_RS_CRAFTED=<dir> cargo test -p ace-pool --test hung_tasks crafted -- --ignored --nocapture`, which runs `test-pool parsers --task-user ace-rs-task --concurrency 1`, queues dmg_analyzer on each DMG and then the CVE module on the image it added, if any; three runs, debug builds of the pool, each time from a task's queuing to its root's idle. `tools/samples/make-macos-hostile DIR` writes the files; it says how each is made. The dev bucket ran with `ACE_RS_BUCKET_MEM_LIMIT=3g` (below).

Each task has ace3's `maximum_analysis_time`, 60 s, and each run of dmg2img or 7z the task's time left less 5 s, as ace3 gives them no timeout of their own. Every run has the runner's limits: 4 GiB of address space, CPU seconds of the timeout times the cores, a 1 GiB file size, 1,024 open files, 64 MiB of stdout and of stderr.

Every run ended inside its limits, with why in the result. Where ace3's modules only log a run the sandbox stopped (`dmg.py`, `cve.py`), the port's results have `stopped`.

ace3 on the same files (`run_module.py --module cve_2021_30657_analyzer --enable dmg_analyzer --dump-file <name>.img`, one run each, in ace3's dev container): its sandbox stops dmg2img on the bombs for the file size and on `runs_5m` for output, and 7z on `deep_long` for output and on the zip bomb for the file size, as here; on the folder cycle its 7z fails to write the script (`errno=36 : File name too long`, under its absolute `-o` directory), and it logs `failed to extracted`; on 5,000 scripts it adds 498 and takes 175 s, as its root holds at most 500 files and the DMG and image are two of them. ace-rs's core has no such limit, so the module stops at 500 of its own, `MAX_FILES`, as the other sandbox modules do.

What the first run of these found, and what changed:

- The folder cycle failed the CVE module's task: the runner, keeping 7z's tree, couldn't move a file whose path is 7.7 KB (`keeping its outputs: File name too long (os error 36)`), and took that as the node's fault. A tool's file whose path no system call takes is now left behind, as one that isn't a plain file is (`ace_sdk::tools::collect_outputs`, and its test `a_tree_too_deep_for_a_system_call_is_left_behind`), which is ace3's outcome too.
- The dev stack's bucket, SeaweedFS under its 1 GiB `mem_limit`, was OOM-killed partway (exit 137, `OOMKilled: true`), and the next task waited for it until the test's 600 s ran out. With 3 GiB it peaked at 982 MiB (`docker stats`). This is what batch 11 found with upx's 400 MB output; the default isn't changed here, and it stays for the owner.
- The table-only DMGs first had an empty data fork, so their property list sat at offset 0, which dmg2img calls corrupted (`XMLOffset` 0); they now have a sector of data fork, so dmg2img parses their tables.

Not made: an APFS image. No Linux tool writes a populated APFS volume (apfsprogs' `mkapfs` makes an empty one, and filling it needs the kernel module), so 7z's APFS reader isn't measured here. libdmg-hfsplus can't add more than about 47 folders of 255-character names (its index records fail its own key check), so the long-name trees use 100 characters.
