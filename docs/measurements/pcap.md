# The pcap modules on crafted captures

PLAN.md 7.5 batch 13: `pcap_analyzer` and the four categories (`pcap_http`, `pcap_files`, `pcap_dns`, `pcap_tls`) on captures made to cost tshark most, contained, as a pool runs them. Measured on 2026-11-10 in ace-rs's dev container (Rancher Desktop, Linux 6.18, aarch64, 10 CPUs) with `ACE_RS_CRAFTED=<dir> cargo test -p ace-pool --test hung_tasks crafted -- --ignored --nocapture`, which runs `test-pool parsers --task-user ace-rs-task --concurrency 1`, queues pcap_analyzer on each capture, then the four categories once it's done; three runs, debug builds of the pool, each time from a task's queuing to its root's idle. `tools/samples/make-pcap-hostile DIR`, run in the dev container, writes the files from frames made by hand (`tools/samples/pcaplib.py`); it says how each is made.

Every tshark and capinfos run has the runner's limits and ace3's `pcap` section's: 120 s a tshark run and 30 s for capinfos, 4 GiB of address space, CPU seconds of the timeout times the cores, a 256 MiB file size (ace3's `pcap.sandbox`), 1,024 open files, 64 MiB of stdout and of stderr. The task has ace3's `maximum_analysis_time`, 360 s, and pcap_analyzer starts only when capinfos and both runs can fit in it (330 s).

The categories took 0.9 to 1.9 s after each. Every run ended inside its limits, with why in the result.

ace3 on the same files (`run_module.py --module pcap_files --enable pcap_analyzer`, one run each, in ace3's dev container) ends each the same way, with the same summaries and errors: the output cap on the DNS flood and on the scan's statistics, the allocation failure on the gzip bomb, the 120 s timeout on the quadratic header (243 s in all), the tree depth on the nested frames, and the same counts on the reassembly and the 20,000 objects (31 s and 7 s).

What the first run of these found, and what changed:

- The 20,000 objects failed pcap_analyzer's task, as the node's fault: `running tshark: a frame of 2040143 bytes`. The supervisor's answer names every file a run kept, and 20,000 paths are past the protocol's 1 MiB frame. The runner's filter and Landlock are unchanged. Two narrow changes: an answer, which only the supervisor writes, may be 16 MiB (`ace_pool::tools::MAX_ANSWER_FRAME`), while a request, which the task writes, stays at 1 MiB; and a run keeps at most 50,000 files and 4 MiB of their names (`ace_sdk::tools::MAX_KEPT_FILES`, `MAX_KEPT_NAME_BYTES`), the rest going with its working directory, so an answer always fits. `containment.rs`' `a_run_keeps_at_most_max_kept_files` keeps 50,000 of 50,010 files and frames their answer. A capture with more than 50,000 objects lists the first 50,000 by name, where ace3 lists them all; it carves 100 either way.
- tshark's field run keeps what it exported when the file size limit stops it (`ToolRun::keep_stopped`), as ace3 collects what tshark wrote before SIGXFSZ. No crafted capture reached that limit: the gzip bomb meets the address space first.

Not made: a capture that makes a 4.4.19 dissector loop for ever. The quadratic HTTP header stands in for one: it doesn't end inside any timeout, and the timeout stops it.
