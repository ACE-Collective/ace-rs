How ace3 and ace-rs analyze a root

ace3 locks a root to one worker, which runs its modules one after another. ace-rs turns every module run into a task in one shared queue. What follows covers how that changes per-root time, total throughput, and where each design pays. The last section asks which model would suit AWS Lambda.

In short: ace-rs doesn't reserve CPUs for a root, so it doesn't give up throughput to make roots faster. A root owns tasks, not workers. When the stack is quiet, one root's tasks take every free slot and the root finishes sooner. When it's busy, every root's tasks share the same slots, and per-root time grows as it does in ace3.

Under load, both designs are limited by capacity divided by the work per root. ace-rs gets more done with the same machines because waiting on the network doesn't hold a worker. In return it pays a cost for every module run, puts more load on Postgres, and keeps roots less isolated from each other.

1. ace3: one root, one worker, one module at a time

A worker takes the lock on a root and keeps it until the root's analysis finishes. It runs each eligible module in turn, in its own process. When a module waits on Splunk, RDAP or a vendor API, the whole worker waits with it, holding the lock and the 400 MB to 1 GB of memory that a Python engine worker holds in production.

2. ace-rs: every module run is a task in one queue

The tree is rows in Postgres. When a result lands, the core works out which (observable, module) pairs it has just made eligible and queues a task for each one. Pools of workers lease tasks from that queue through the core's API, oldest due task first, from any root. Each module writes its own rows, so no root lock is needed. A root is complete when none of its tasks is queued or running.

3. Load decides whether a root gets faster

The speedup above relies on there being free slots. Once several roots are in the stack, their tasks compete for the same slots and each root waits its turn, as ace3's roots wait for a free worker. In this measurement, total throughput went up and per-root time went up much more.

Light load

ace-rs: one root takes every free slot, so its time is close to its critical path.

ace3: the root runs in series on one worker however many workers are idle.

The difference is how much useful work the same hardware does, and how latency is shared between roots. The next two sections cover each.

5. What ace-rs pays for it

A cost for every module run

In ace3, a module that turns a file down costs one function call. In ace-rs, every module run goes through the whole task lifecycle:

Postgres coordinates everything

Every task is several writes, a lease and a notification, and each new result triggers an eligibility check. ace3 handles all of this in memory inside one worker. At production scale, the first limit ace-rs reaches is more likely Postgres's write rate than CPU.

Modules that run last have to wait

Six modules run only once the rest of their root is finished. Because no worker owns the whole root, each of them has to ask whether the others are done and wait if they aren't. Before the core started waking them, this waiting was 30% of a root's time. Some of it remains where files are nested inside other files.

Roots are less isolated from each other

This is the real tradeoff behind the intuition that ace3 handles more roots in parallel. The ace-rs queue leases the oldest due tasks, with no per-root fairness or priority. A large root that queues thousands of tasks at once gets ahead of a small alert that arrives just after it:

7. Which model suits AWS Lambda?

Lambda runs one function per invocation, for at most 15 minutes. It bills every millisecond of wall-clock time at the configured memory size, and it may freeze an environment between invocations or discard it.

ace-rs fits much better, but only for some of its work. Run the parser pool on Lambda, and the sandbox pool for short tools. Keep the core, Postgres and the lookups pool on long-running compute such as ECS or Fargate. ace3's model doesn't fit Lambda.

ace3: doesn't fit

  • A worker holds a root for its whole analysis, which can take many minutes. A root that runs past 15 minutes is killed partway through.
  • Network waits are billed at the full memory size.
  • A cold start has to load about 230 MB of Python imports before any work starts.
  • The lock's heartbeat stops while Lambda has the environment frozen, so the lock can expire with the work half done.

To run on Lambda, a root's analysis would have to be split into resumable pieces, which is what ace-rs already does.

ace-rs: mostly fits

  • The unit of work is a short, stateless task, and file bytes are already in an S3-compatible bucket.
  • If an invocation dies, its lease expires and the reaper queues the task again.
  • Pools lease through the core's API and never connect to Postgres, so a thousand Lambdas don't mean a thousand connections.
  • ace-parsers task already runs one task and exits, so a Lambda handler could wrap it.
  • Parsing comes in bursts, and Lambda scales up for a burst and back to zero afterwards.

Where ace-rs still fits badly

The lookups poolIt saves money by running many network calls concurrently in one process. On Lambda, every call would wait in an invocation of its own that's billed by the millisecond. Keep it on a container.
Per-task overheadEach task would add an invocation, and sometimes a cold start, to what it already costs. That makes the module "takes" declarations, which stop declining tasks from being queued, essential rather than optional.
