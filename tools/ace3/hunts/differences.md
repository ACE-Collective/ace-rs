# Differences between ace3's and ace4's hunt loading and template rendering

PLAN.md 6.2. `make-hunts` writes what ace3's loader makes of each hunt, its normal form or its error, to `reference/`: `cases.json` for the hunts in `cases/`, written to cover each of ace3's errors and the YAML and coercion rules a hunt can trip on, and `signatures.json` for the signatures checkout. ace4's loader (`crates/ace-hunt`) writes the same shape. `the_cases_load_as_they_do_in_ace3` (`crates/ace-hunt/src/normal.rs`) diffs the cases and `compare` the signatures, and each fails on a difference no row here explains and on a row that explains nothing.

PLAN.md 6.3. `make-templates` renders hunt templates with ace3's own Jinja code (`render_templates.py`) and writes each result to `reference/`: `templates-cases.json` for `templates/cases.yaml`, templates written to cover each filter, test and global, undefined values in both modes, whitespace, loops, macros and ace3's event expansion, and `templates-signatures.json` (git-ignored) for every template of every hunt in the signatures, each rendered with the call ace3's hunter makes for it against fixed events built from the fields the hunt reads. `the_template_cases_render_as_they_do_in_ace3` (`crates/ace-hunt/src/render/compare.rs`) diffs the cases and `compare-templates` the signatures, with the sets `templates-cases` and `templates-signatures`. A render's key is `<template> <call> <event>` for a case and `<where in the hunt> <event>` for a hunt.

PLAN.md 6.4. `make-query-hunts` runs ace3's Splunk hunter (`run_query_hunts.py`) over the hunts in `query/hunts`, at the ticks `query/runs.yaml` gives, against `tools/ace3/dumps/fake_splunk.py`, and writes every exchange, each staged submission and the hunt's state after each tick to `reference/query.json`. `the_cases_submit_as_ace3_s_hunter_does` (`crates/ace-app/src/hunter/tests.rs`) replays the exchanges to ace4's hunter and diffs its submissions, with the set `query`: a submission's key is `<hunt file> tick <n>` and its path starts at `/submissions/<i>`. The job forms, the skipped ticks and the state must match with no row.

PLAN.md 6.6. The `correlated*.yaml` cases run ace3's correlation engine in the same run, its queries to the same fake through ace3's `SplunkQuerySource`; their job forms, including each correlation query's, must match with no row, and the submissions carry the correlation's trace, the original rows and the provenance in their details.

A row needs a reason someone verified by reading both systems' code and looking at the values. Set is `cases`, `signatures`, `templates-cases` or `templates-signatures`. In the Hunts column `*` matches any text in a hunt's path. The Path column is a JSON pointer into the hunt's entry: a `*` segment matches one segment, `**` any number, and a `*` inside a segment any text.

Where ace4 raises the error ace3 does but words it differently, the row says so: the class, the location and pydantic's error type always match, and the text is ace3's except where a row names it (PLAN.md's brief on the scope of a port: match what the loader does with the file, not the wording of a parser's message).

## The hunt scripts' command types

PLAN.md decision 16. `make-scripts` runs each of the signatures' 7 hunt scripts in ace3's container over `scripts/cases.json`, cases written for this with DNS, HTTP and TLS faked from each case, and writes each case's exit code, stdout, the last line of its stderr and the calls it made to `reference/scripts.json`. `each_script_type_matches_its_script` (`crates/ace-hunt/src/correlate/scripts/cases.rs`) runs ace4's script command types over the same cases with the same fakes: the exit code, the stdout byte for byte, the calls in order and an uncaught exception's class must match, with no row. All 113 cases do.

What the cases can't show, each checked against both systems' code. None of it changes a script's output on the signatures' commands.

- **stderr.** A script's stderr reaches only a failed step's error. ace4 gives the same exit code and the same exception class, but the words are its own: argparse's usage line is shorter, an uncaught exception is its last line without the traceback, and `signature_name_12`'s count of what it dropped isn't written.
- **Environment.** ace3's runner hands a script an allowlist of its process's variables (PATH, the locale, the proxy and CA bundle variables) and the command's `env:`. A script type sees only the command's `env:`, and no type reads one: `removed_hunt_one.py` reads `CERT_OWNERSHIP_CA_BUNDLE`, for extra roots on an analyst's workstation, and ace4's probe trusts the platform's roots only, as the script does on ACE's server.
- **Files.** A script type reads the files the command stages, by the names the script would see beside itself, and from the hunt repositories only, as ace3's staging requires. `signature_name_12.py --allowlist` with an absolute path reads nothing in ace4, where in ace3's sandbox it could read anything the runner allows; the signatures' commands don't pass it.
- **Python's libraries.** `signature_name_12`'s allowlist patterns compile with the `regex` crate, not `re`: a pattern with a lookaround or a backreference doesn't compile, and the allowlist is then unreadable and not applied, as the script does with one `re` can't compile; the signatures' two patterns compile in both. `signature_name_13` encodes a label past ASCII with UTS #46 where Python's `idna` codec uses IDNA 2003's nameprep on Unicode 3.2; they agree but for the deviation characters the script refuses first and characters Unicode added since. A bin's number past 1.7e38 drops its row in ace4, where Python's integers have no bound.
- **The network.** Each call of the real network (`ace_app::hunter::net`) gives the outcome dnspython or urllib would, but where a failure's text is the library's (a URLError's reason, a DNS error's message) the words are ace4's. DNS is `ace_mod_dns::resolve`, dnspython's stub resolver ported for the DNS module; a nameserver that can't be reached, which `resolve` gives up on before the lifetime ends, is dnspython's LifetimeTimeout, as dnspython 2.9.0 reports both a refused and an unroutable nameserver. An IPv4-compatible IPv6 address (`::1.2.3.4`) is written `::102:304`, as Rust writes it. `removed_hunt_one`'s handshake is rustls with the platform's roots, where Python's is OpenSSL's: rustls has no TLS 1.0 or 1.1 and fewer cipher suites, and webpki's checks of a chain are its own, so a server only OpenSSL can talk to, or a chain only OpenSSL accepts, is an error and the pair's confidence `unknown`, which keeps it alerting.
- **Settings.** `removed_hunt_three.py` holds its home tenant and its lexicon of impersonation words in its code; ace4 reads both from the hunter's configuration (`scripts.removed_hunt_three`), and without a home tenant the type doesn't build and its steps fail. The cases set both, in ace3 by setting the script's constants before its `__main__` block runs.
