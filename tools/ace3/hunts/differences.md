# Differences between ace3's and ace4's hunt loading and template rendering

PLAN.md 6.2. `make-hunts` writes what ace3's loader makes of each hunt, its normal form or its error, to `reference/`: `cases.json` for the hunts in `cases/`, written to cover each of ace3's errors and the YAML and coercion rules a hunt can trip on, and `signatures.json` for the signatures checkout. ace4's loader (`crates/ace-hunt`) writes the same shape. `the_cases_load_as_they_do_in_ace3` (`crates/ace-hunt/src/normal.rs`) diffs the cases and `compare` the signatures, and each fails on a difference no row here explains and on a row that explains nothing.

PLAN.md 6.3. `make-templates` renders hunt templates with ace3's own Jinja code (`render_templates.py`) and writes each result to `reference/`: `templates-cases.json` for `templates/cases.yaml`, templates written to cover each filter, test and global, undefined values in both modes, whitespace, loops, macros and ace3's event expansion, and `templates-signatures.json` (git-ignored) for every template of every hunt in the signatures, each rendered with the call ace3's hunter makes for it against fixed events built from the fields the hunt reads. `the_template_cases_render_as_they_do_in_ace3` (`crates/ace-hunt/src/render/compare.rs`) diffs the cases and `compare-templates` the signatures, with the sets `templates-cases` and `templates-signatures`. A render's key is `<template> <call> <event>` for a case and `<where in the hunt> <event>` for a hunt.

A row needs a reason someone verified by reading both systems' code and looking at the values. Set is `cases`, `signatures`, `templates-cases` or `templates-signatures`. In the Hunts column `*` matches any text in a hunt's path. The Path column is a JSON pointer into the hunt's entry: a `*` segment matches one segment, `**` any number, and a `*` inside a segment any text.

Where ace4 raises the error ace3 does but words it differently, the row says so: the class, the location and pydantic's error type always match, and the text is ace3's except where a row names it (PLAN.md's brief on the scope of a port: match what the loader does with the file, not the wording of a parser's message).

| Set | Hunts | Path | Why |
|---|---|---|---|
| cases | `hunts/splunk/yaml_syntax.yaml` | `/error/message` | Both raise PyYAML's ScannerError for the same token, at the same line and column. The text is yaml-rust2's, which ace4 parses with, where ace3's is PyYAML's: "mapping values are not allowed in this context" for "mapping values are not allowed here". |
| cases | `hunts/splunk/include_syntax.yaml` | `/error/message` | Both raise a ParserError for the unclosed flow sequence in the include, at its end. PyYAML also names where the sequence began, and words it "expected ',' or ']', but got '<stream end>'"; yaml-rust2 says "while parsing a flow sequence, expected ',' or ']'". |
| cases | `hunts/splunk/include_spelled_loop.yaml` | `/error/*` | `spelled.include.yaml` includes `../spelled_back.include.yaml`, which includes `deeper/spelled.include.yaml`: a loop whose path grows by `deeper/../` each time round. ace3 remembers the files it has read by the text of their paths, so it never sees the loop and recurses until the path is too long to open (OSError, ENAMETOOLONG). ace4 keeps that rule, so a loop spelled the same way each time is skipped as in ace3 (`include_loop.yaml`), but it also stops at a file already being read further up the chain, by its real path, and fails the hunt there with an ace4 limit. Both fail the hunt. |
| cases | `hunts/splunk/ok_minimal.yaml` | `/*` | `duplicate_name.yaml` has the same name. ace3's HuntManager fails whichever of the two it lists second, and it lists a directory in `os.scandir` order: on the tmpfs make-hunts copies the cases to, that's newest first, so reverse name order, and `ok_minimal.yaml` loads. ace4 lists by name, so `duplicate_name.yaml` loads and this one fails with ace3's `KeyError('duplicate hunt ok minimal')`. |
| cases | `hunts/splunk/duplicate_name.yaml` | `/*` | The other side of the row above. |
| templates-cases | `filters-text` | `/renders/13 jinja 1` | `{{ s\|reverse }}` where `s` is undefined. Jinja's `do_reverse` returns `reversed(value)`, an iterator, which Python prints with its address (`<reversed object at 0xffff...>`); ace4's `reverse` returns a list, which prints `[]`. Iterating, joining or `\|list` give the same in both (`filters-sequences` checks them); only printing the iterator itself differs, and its address can't match. |
| templates-cases | `methods` | `/renders/17 *` | `{{ d.items }}` prints the bound method, which Python writes with its address (`<built-in method items of dict object at 0x...>`). ace4 writes the same without an address, which can't match. |
| templates-cases | `methods` | `/renders/20 *` | `{{ [1, 2].append }}`, the same as the row above for a list's method. |
| templates-cases | `control` | `/renders/32 *` | `lipsum()` makes random Lorem Ipsum (`jinja2/utils.py` `generate_lorem_ipsum`), so no two renders match, not even ace3's. ace4 doesn't provide it: the call fails, as calling an undefined name does (an UndefinedError under StrictUndefined). No hunt uses it. |
| templates-cases | `control` | `/renders/35 jinja_strict 0` | `{{ s\|format(1) }}`: the `format` filter is printf-style formatting (`soft_str(value) % args`), which ace4 doesn't port; ace4 fails with an unknown filter where ace3, under StrictUndefined, raises UndefinedError for the undefined `s` before formatting. Under the default Undefined both fail. No hunt uses `format`. |
| templates-cases | `control` | `/renders/36 *` | `{{ '%s and %s' % ('a', 'b') }}`: Python's printf-style `%` on a string, which ace4 doesn't port (`ops::rem` fails it with a note). No hunt template uses it. |
| templates-cases | `control` | `/renders/37 *` | `{{ 'a {}'.format(1) }}`: `str.format`, which the sandbox allows and ace4 doesn't port (`methods` fails it with a note). No hunt template uses it. |
| templates-cases | `shared-event` | `/renders/all shared 0/1` | ace3's hunter renders every template of a hunt against the same event dict, and two things let one render change the next: a template's `append` or `update` on a list or dict from the event changes it in place, and `_expand_dotted_keys` writes a flat key's value into the event's own nested dict when both `device` and `device.hostname` are keys. So the second template here sees `[1, 2]` and `flat`. ace4 renders each template against its own copy of the event, so it sees the event as it came: `[1]` and `nested`. No hunt template changes an event's values, and the signatures' events don't carry both forms of a key. |
